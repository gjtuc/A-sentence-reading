# 374 — 다시 물어볼지는 서버가 말한다

## 왜

0.3.414 에서 사용자가 문장 몇 개를 읽었다. **첫 문장만 채점되고 그 뒤는 전부 채점이 안
됐다.** 로그의 흐름이 그대로 보여준다.

```
10:40:12  sound_retry  stale_span_n=12   <- design/373 이 옛 행을 버리고 서버에 물음
10:40:12  spoken_ok    span_n=13         <- 서버는 queued, 소리는 아직 없음
10:40:32  cache_hit    phone_span_n=0    <- 소리 없는 행을 그대로 유지
          -> slot_code = sound_ref_missing
```

문장 2, 3 도 똑같았다.

design/371 은 재요청을 **실행당 한 번**으로 묶었다. 서버가 기준을 끝내 만들 수 없을 때
문장을 볼 때마다 호출이 나가는 것을 막기 위한 상한이었고, 그 땐 충분했다. design/373 이
옛 형식 행을 버리기 시작하면서 충분하지 않게 됐다. **옛 행을 발견하는 데 그 한 번을 쓰고
나면**, 그 자리를 채운 답은 아직 만들어지는 중이고, 그 문장은 그 실행이 끝날 때까지
비교할 것이 없다.

## 잠금

### 횟수가 아니라 서버가 정한다

서버는 자기가 무엇을 하는 중인지 이미 말하고 있었다. `/api/tts/spoken` 의 `sound_ref_code`
다. 폰이 그걸 읽지 않았을 뿐이다.

| 답 | 뜻 | 다시 묻나 |
|---|---|---|
| `queued` · `building` | 만들고 있다 | **묻는다** |
| `ready` | 있다 | 필요 없다 (소리가 채워져 있다) |
| `empty` | 기준은 있지만 이 단어들을 못 집었다 | 묻지 않는다 |
| `off` · `sunk` · `busy` · 실패 이름 | 오지 않는다 | 묻지 않는다 |
| 없음 | 서버가 말하지 않았다 (0.3.415 이전) | 상한까지 묻는다 |

기준을 끝내 못 만드는 서버는 **한 번** 호출되고 끝난다. design/371 보다 싸다.

### 없는 것은 거절이 아니다

`sound_ref_code` 가 아예 없으면 옛 서버다. 그걸 거절로 읽으면 옛 서버에 붙은 폰은 아무
것도 채점하지 못한다. 그래서 빈 값은 상한을 그대로 쓴다.

### 상한은 남는다

`kSoundAskMax = 3`. 큐에 걸린 빌드는 계속 `queued` 라고 답하므로, 문장을 볼 때마다 호출이
나가는 일은 여전히 막아야 한다. 제작은 8초쯤 걸리고 문장은 그보다 오래 화면에 있으니 3이면
기다림을 덮는다. **이 상한을 없애지 말 것.**

### 실행 안에서만 산다

`_refCode` 는 디스크에 쓰지 않는다. 그것은 **진행 중인 제작**을 설명하는 값이고, 다음
실행에서 제작은 진행 중이 아니다. `setSpeakNorm` 은 행을 버리므로 예산과 코드도 함께
버린다.

## 증거

`practice_skill_spoken` 행에 둘이 더 붙었다.

- `ask_n` — 이 문장이 이번 실행에서 다시 물은 횟수
- `ref_code` — 서버가 마지막으로 한 말

`cache_hit` 에 `phone_span_n: 0` 이 있는데 `ref_code` 가 `queued` 이고 `ask_n` 이 상한
미만이면, 그건 이 설계가 깨진 것이다.
