# 378 — 기준 소리는 논문 분석할 때 만든다

## 무엇이 문제였나

0.3.416 로그에서 문장 하나가 채점을 아예 건너뛰었다. 이유는 `sound_ref_missing`, `ref_n=0` —
그 문장의 원어민 기준 소리가 아직 없었다. 서버는 16:13:51 에 `queued`, 16:14:13 에 다시
`queued` 라고만 답했고, 읽은 것은 16:14:26 이었다.

채점을 포기한 것 자체는 옳다. 비교할 상대가 없는데 "다 틀렸다"고 하면 거짓말이다.

문제는 **왜 기준이 없었나** 다. design/371 이 기준을 만들게 해놓고, **만들 시점을 읽는 순간으로
두었다**. 짓는 데 15–32초가 걸리고 일꾼은 하나다. 그래서 새 논문의 첫 바퀴는 아직 안 지어진
문장마다 채점을 건너뛴다.

### 한 번만 생기는 일이 아니다

처음엔 design/373 이 옛 형식 캐시를 전부 다시 지으라고 해서 줄이 밀린, 한 번뿐인 일이라고
적었다. 틀렸다. `request_build` 를 부르는 곳은 `routes/tts.py` 의 문장별 TTS 경로 **하나뿐**이고,
분석 쪽에는 미리 짓는 단계가 아예 없었다. `reference_for` 의 설명문이 이미

> A caller on a request path should pass `allow_build=False` and let a warm step
> do the synthesis

라고 적어두었는데, **그 warm step 이 존재하지 않았다**. 그러니 논문을 새로 분석할 때마다 같은
일이 생긴다.

## 고친 것

분석이 끝나는 자리(`_finish_job`)와 캐시된 논문을 여는 자리에서, 그 논문의 모든 문장에 대해
기준 소리를 미리 짓는다. 사장님이 처음에 말한 설계가 이것이다 —
「처음에 논문 분석할 때 TTS로 원어민의 음성을 따 놓고」.

문장 목록은 캐시된 세션에서 꺼내고, **폰이 보낼 문자열과 똑같이** `spoken_text_for_tts` 를
통과시킨다. 캐시 열쇠가 말하는 형태로 잡히므로, 이 변환을 빠뜨리면 미리 지은 것이 하나도
쓰이지 않는다.

## 읽는 사람이 줄 뒤에 서면 안 된다

이게 이 설계의 핵심이고, 틀리기 쉬운 자리다.

일꾼은 하나다(`max_workers=1`). 논문 300문장을 한꺼번에 큐에 넣으면 지금 화면에 있는 문장이
**300번째**가 된다. 지금보다 나쁘다.

그래서 `warm_paper` 는 하나 넣고 큐가 빌 때까지 기다린 뒤 다음을 넣는다. 읽는 사람이 요청하면
**최대 한 개의 작업 뒤**에 선다. 논문 하나 뒤가 아니다. 요청이 계속 들어오면 미리 짓는 쪽이
계속 양보한다 — 읽는 사람이 항상 이긴다.

시험 `test_warm_waits_for_the_queue_to_clear` 가 이걸 지킨다. 제출 순간의 큐 깊이가 매번
0이어야 통과한다.

## 멈추는 조건

| 조건 | 왜 |
|---|---|
| `enabled()` 거짓 | 기능이 꺼져 있다 |
| `_BUILD_RUN >= BUILD_GIVE_UP` | 짓기가 연달아 실패하면 한 문장당 합성 한 번씩 돈을 내며 배운다 |
| `WARM_BUDGET_S` (3시간) 초과 | 실이 자기가 데우던 것보다 오래 살지 못하게 |
| 이미 캐시에 있음 | 값싸게 넘긴다 (`warm_ready`) |
| 같은 `cache_id` 가 이미 데워지고 있음 | 재분석이 실을 쌓지 못하게 |

## 이어서 짓기

긴 논문은 40분이다. Cloud Run 은 `--no-cpu-throttling --min-instances 1` 이라 배경 실이
돌기는 하지만, 그 인스턴스가 40분을 살아 있다고 보장할 수는 없다. 그래서 **여는 자리에도**
붙였다. 끊긴 데서 이어지고, design/378 전에 분석한 논문도 채워진다.

## 증거

`sound_ref_warm` — `stage=start` 에 `warm_n`, `stage=done` 에 `warm_built` / `warm_ready` /
`warm_failed` / `warm_skipped`, `stage=fail` 에 `warm_fail`.

`start` 를 따로 적는 이유: 중간에 끊긴 데우기와 아예 시작도 안 한 데우기가 로그에서 같아
보이면 안 된다.

## 재볼 것

```
python scripts/warm_paper_probe.py --lines 2
```

실제로 Google 을 부른다. 데운 뒤에 `allow_build=False` 로 다시 물어서, 읽는 경로가 묻는 것과
똑같은 질문을 한다 — 인쇄된 단어마다 소리가 붙어 있나. 재본 결과 2문장 53초, 15/15 단어
전부 물어볼 수 있는 상태(소리 3개 이상)였다.

## 하지 말 것

- 논문 전체를 한 번에 `request_build` 로 밀어넣지 말 것. 읽는 사람이 논문 뒤에 선다.
- `spoken_text_for_tts` 를 건너뛰고 인쇄된 문장 그대로 데우지 말 것. 열쇠가 어긋나 전부 헛일이 된다.
- 데우기를 요청 경로에서 기다리지 말 것. `warm_paper` 는 막는 것이 설계이므로 실에서 불러야 한다.

## 남은 것

이건 **기준이 제때 있게** 만든 것이다. 기준이 **맞는지**는 다른 문제다 — design/377 이 재본
단어별 천장이 0.429 까지 내려가는 것(`nanoparticles`), 즉 어떻게 읽어도 통과선을 넘을 수 없는
단어가 있다는 쪽은 아직 원인을 찾는 중이다.
