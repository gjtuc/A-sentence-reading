# design/381 — 모델이 얼마나 확신하는지를 점수로 쓴다

## 사장님이 그린 표

```
    A  B  C  D
 a 0.1
 b 0.1
 c 0.03
 d 0.77
```

기준 소리 하나는 「d가 0.77」 같은 분포를 가지고 있다. 사용자가 그 자리에서
0.73을 냈다면 그 소리는 1.0 만점에 0.9점쯤 받은 것이다. 소리 점수를 단어로
모으면

```
T 0.76   h 0.86   e 1.00   →  (0.76+0.86+1.00)/3 = 0.873
```

이 단어는 기준 x보다 높다/낮다 → 그 단어가 탈락인가 아닌가. 문장 안에서
`the 합 ant 합 is 불합 small 합` 이면 정확도 0.75. 그 정확도가 블록에 누적되어
블록 한 개의 인식률이 되고, 블록 인식률의 평균이 다음 난이도를 올릴지 내릴지
정한다.

## 지금까지 왜 안 돌고 있었나

설계는 2개 단계로 나뉘어 있었다.

- **1단계 (돌고 있음)** — 가장 그럴듯한 소리 하나만 뽑아서 글자처럼 비교한다
  (`overlap_ratio`). 확률은 버린다.
- **2단계 (사장님 설계, 안 돌고 있었음)** — 확률을 그대로 쓴다.

1단계를 먼저 올리고 2단계를 뒤에 하기로 했는데, 돌아오지 않았다.
`phone_frames` 는 `argmax` 하고 확률을 버린다. 그래서 모델이 0.35로 겨우 찍은
소리와 0.97로 확신한 소리가 채점에서 똑같은 무게를 가진다 (design/380).

## 이번에 붙인 것 — 재는 것까지

새 의존성 없이 직접 구현했다.

### `sound_align.py` — CTC 강제 정렬

`[blank, t0, blank, t1, ...]` 로 늘린 수열 위에서 Viterbi (제자리 / 한 칸 /
두 칸, 두 칸은 목표가 blank 가 아니고 두 칸 전과 다를 때만), 되짚기, 그 다음
토큰마다 자기 프레임들의 확률 평균. 이것이
`torchaudio.functional.merge_tokens` 가 내놓는 수치와 **같은 정의**다.

`tests/test_sound_align.py` 가 11개 난수 씨앗에서 `torchaudio.functional.forced_align`
+ `merge_tokens` 와 토큰·시작·끝·점수를 1e-5 안에서 맞춘다. 서버 이미지에는
`torchaudio` 를 넣지 않았다.

### `hear_waveform.py` — 확률표를 한 번의 추론에서 꺼낸다

`hear_phones_sheet(data)` 가 `(소리, 확률표, 보고)` 를 준다. 확률표는 이미 하던
그 한 번의 모델 호출에서 `log_softmax` 로 나온 것이다. **녹음 한 개가 추론을
두 번 하지 않는다.** `certainty_of(sheet, groups)` 가 단어별 소리별 확신도를
리스트로 준다. 평균으로 줄이지 않는 이유는 아래에 있다.

### `/api/stt/recognize` — 재서 적는다

폰이 이미 가지고 있는 기준 소리를 `target_phones` 로 `|` 로 이어 보낸다. 서버가
다시 만들지 않으므로 답이 폰의 칸 순서와 **구조적으로** 맞는다. 돌아오는 것은
`slot_sure` (단어별 평균, 100분율), `slot_floor` (그 단어에서 가장 확신 못 한
소리, 10000분율), `sure_code`.

**아직 채점하지 않는다.** 1단계 점수와 2단계 확신도가 같은 녹음에 대해 한 줄에
같이 적힌다. 통과선은 사장님의 실제 녹음으로 다시 재서 정한다 — design/375 의
선도 그렇게 나왔고, 합성 음성에서 뽑은 숫자를 그대로 쓰면 안 된다.

## 왜 평균만으로는 안 되는가 — 재본 것

`scripts/certainty_score_probe.py`. 이웃 단어로 바꿔 읽은 5쌍.

| 바꾼 것 | 맞게 읽음 평균/최저 | 틀리게 읽음 평균/최저 | 평균 차 |
|---|---|---|---|
| loss → lost | 0.785 / 0.4116 | 0.822 / 0.4996 | **−0.037** |
| stable → table | 0.949 / 0.8439 | 0.754 / 0.0001 | +0.195 |
| prepared → repaired | 0.795 / 0.4211 | 0.673 / 0.0000 | +0.122 |
| dispersed → disperse | 0.902 / 0.5965 | 0.849 / 0.5488 | +0.054 |
| measured → treasured | 0.905 / 0.7784 | 0.721 / 0.0000 | +0.184 |

`loss → lost` 는 평균이 **거꾸로** 나온다. 틀리게 읽은 쪽이 더 높다. 기준의
소리가 다 들어 있고 읽은 사람이 더 말했을 뿐이기 때문이다.

최저값 1% 문턱: 5개 중 3개를 잡고, 맞게 읽은 5개와 건드리지 않은 35개 단어에서
잘못 잡은 것이 **0개**. 안 낸 소리는 거의 0으로 돌아오고 평균은 그것을 못 보여
준다. 그래서 `certainty_of` 는 소리별로 돌려준다.

나머지 2개(`loss`/`dispersed`)는 **더 말한 소리**를 세야 잡힌다. 619개 사람
녹음으로 확정한 설계가 「평균 + 최저 1% + 더 말한 소리」 세 부분이었던 이유가
여기서 독립적으로 다시 나왔다.

한 단어를 바꿔도 나머지 단어 평균은 0.870 → 0.869. 정렬이 한 단어의 오독 때문에
문장 전체를 흔들지 않는다.

## 다음

1. 실제 녹음에서 `slot_sure`·`slot_floor` 를 모아 통과선을 2단계 척도에서
   다시 잰다. 확정 설계의 초기값 0.489 는 **다른 측정에서 나온 숫자이므로
   재사용하지 않는다.**
2. 판정을 평균 + 최저 1% + 더 말한 소리로 바꾼다.
3. 「더 말한 소리」는 정렬이 준 각 단어 구간 안의 argmax 길이를 기준 개수와
   비교해서 센다.
