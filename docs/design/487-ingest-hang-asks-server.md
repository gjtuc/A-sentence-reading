# 487 — 앱이 분석을 포기하기 전에 서버에 묻는다

## 문제

웹(0.3.496)에서 파일 3개를 대기열에 넣었다. 세 번째 파일(4.4MB 보충 자료)이 진행 중일 때 앱이
"응답이 없어 업로드를 중단했습니다"를 띄우고 그 파일을 대기열에서 지웠다. 서버는 그 파일을 계속 분석했다.

기록(UTC):

| 시각 | 서버 | 앱 |
|---|---|---|
| 05:52:51 | 그림 찾기 시작 | |
| 05:53:38 | | 마지막으로 진행을 봄 (그림 찾는 중) |
| 05:55:27 | 그림 45개 끝, 본문 정리 48% | |
| 05:56:24 | 본문 정리 70% | |
| 05:56:36 | | 180초 진행 없음, 포기 |

사용자는 그동안 다른 탭과 프로그램을 보고 있었다. 앱 기록은 매분 ○○:36에만 찍혔다. 숨은 탭은
브라우저가 1분에 한 번 깨우고, 앱도 화면 밖에서는 1분에 한 번만 묻는다(design/396). 포기 시계
(`HangWatchdog.ingestStall` 3분)는 이 사정을 몰랐다.

## 방침

- 번역·본문 정리 구간이 아닐 때 시계가 울리면 `_confirmIngestHang`이 판단한다.
  `ingestHangShouldAbort`의 규칙:
  - 화면 밖이면 포기하지 않고 시계를 다시 건다.
  - 화면에 있으면 `GET /api/ingest/jobs/{id}`를 한 번 묻는다(`peekIngestJob`).
  - 끝났거나 `worker_alive`이면 다시 건다.
  - 답이 없거나, 실패했거나, 일꾼이 없으면 예전처럼 포기한다.
- `public_job_view`는 끝나지 않은 작업에 `worker_alive`를 싣는다. 이 서버가 돌리고 있거나
  lease(25초마다 5분으로 갱신)가 살아 있으면 참이다.
- 기록:
  - `client_hang` `ingest hang held`: 참은 이유(`away`, 서버 진행)
  - `app_visibility` `away` / `back`: 화면 밖에 있던 초
  - `upload_queue_skip`: 대기열에 못 넣은 이유(`empty` / `full` / `dup` / `save_fail`)
- 같은 파일이 이미 대기열에 있으면 "같은 파일 N개는 이미 대기열에 있어 건너뛰었습니다"를 보인다.
- 대기열을 서버로 옮기는 일(탭을 닫아도 다음 파일이 진행)은 따로 계획한다.
